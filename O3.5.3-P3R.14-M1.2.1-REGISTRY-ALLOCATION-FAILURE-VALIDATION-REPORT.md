## 4. Initial Registry allocation failure behavior

`ProgramRegistry.Initialize()` calls `Grow(16)` before registering any built-ins. When `Kernel.OsAlloc` returns null on that first call, `Grow` returns false and `Initialize()` returns false immediately — `TeardownStorage` is not reached (nothing was allocated). Observable result: `Initialized == false`, `Count == 0`, no descriptor findable by id or name, no id consumed (`_nextId` stays 0), no storage retained (allocator recorded exactly one failed call, zero frees). A subsequent `Initialize()` after `Kernel.ResetAlloc()` succeeds, registers built-ins exactly once with ids 1, 2, 3, and the registry is usable. This matches the "failed allocations preserve existing state / atomic initialization" contract.

Source-verified: `EmbeddedRegistry.cs:79–99` (`Initialize`), `EmbeddedRegistry.cs:339–368` (`Grow` — returns false on null ptr before mutating `_descriptors`/`_capacity`).

---

## 5. Lease-table growth behavior

The real acquisition path (`EmbeddedRegistry.Leases.cs:36–67`, `TryAcquireSpawnLease`) grows the lease table via `GrowLeases` only when `FindInactiveLeaseSlot() < 0` and `_leaseSlotCount >= _leaseCapacity`. With an initial capacity of 16, the 17th simultaneous lease for program 1 triggers `GrowLeases(32)` (a real `Kernel.OsAlloc`), which succeeds. All 17 leases hold distinct nonzero tokens (monotonic `_leaseCounter`, token 0 reserved), all 17 release cleanly, descriptor `SpawnLeases` returns to 0, and descriptor data / registry count are unchanged. Growth was exercised through the public acquisition path, not by modifying capacity fields.

---

## 6. Lease-table growth allocation failure behavior

With 16 active leases filling the 16-slot table, forcing the next `OsAlloc` to fail makes the 17th `TryAcquireSpawnLease` return false: `NextLeaseToken()` runs, then `FindInactiveLeaseSlot()` returns -1, then `GrowLeases(32)`'s `OsAlloc` returns null and `GrowLeases` returns false *before* replacing `_leases`. The original table is untouched, `SpawnLeases` stays 16, no invalid lease is created (`out lease` is default), all 16 prior leases remain releasable, count returns to 0, and the registry remains usable. After `Kernel.ResetAlloc()`, a new acquisition succeeds, `GrowLeases(32)` completes, all 17 leases acquire and release, count returns to 0.

---

## 7. Token-generation behavior after failed growth

**Observed behavior (documented, not changed):** `NextLeaseToken()` (`EmbeddedRegistry.Leases.cs:92–103`) is called *before* the table slot/growth in `TryAcquireSpawnLease`. Consequently, when the 17th acquisition fails at the growth step, token 17 has already been consumed (`_leaseCounter` advanced to 17) although no lease entry was created. The next successful acquisition receives token 18 (verified: probe token `== 18`).

Contract assessment:
- Tokens remain **unique** and **nonzero** — the contract is preserved.
- No **active** token is reused; on exhaustion acquisition fails safely rather than reusing an active token.
- The failed allocation preserved the lease table and descriptor state (`SpawnLeases` unchanged at 16).

This is a pre-existing design choice (token allocated before the table slot), not a regression introduced here. It does **not** violate the architecture ("Spawn leases use unique, nonzero tokens"; "failed allocations preserve existing state" — the lease table and descriptor are preserved; only the monotonic counter advances). Per the task instructions, no token semantics were changed and no speculative production fix was applied. If the project later decides a failed acquisition must not consume a token, that would be a separate architectural decision requiring a minimal fix + regression test; it is out of scope for this validation task.

## 10. Remaining limitations

1. **Fresh-state isolation:** The Registry keeps all state as private statics, so one host process cannot construct two independent Registry instances. True per-test isolation would require a production reset API, which the task forbids adding solely for tests. A test-only reset partial class (`RegistryTestReset.cs`, test assembly only) was used — the smallest test-only isolation approach — so Test 1 runs against a genuinely fresh, uninitialized Registry after the pre-existing sections A–E. Test ordering matters; a reset separates sections.
2. **Token consumption on failed growth:** documented above; intentionally not changed.
3. **No QEMU/runtime-on-hardware validation** performed (production unchanged; not required).
4. Tests share static state within a single host process; they are deterministic and bounded but not parallelizable against the Registry.
